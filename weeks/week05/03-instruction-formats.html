5.7   Instruction Formats: R, I and J

An instruction is 32 bits. Look at what three different instructions need to say:

  • add $t0, $t1, $t2 — an operation and three registers.
  • lw $t0, 64($sp) — an operation, two registers and a number.
  • j 8192 — an operation and one large address.

Three different shapes of information, one fixed budget of 32 bits. You cannot give every instruction room for the largest of them, because then add would waste most of its width on a field it does not use.

So MIPS defines three ways of dividing up the same 32 bits, and the processor has to be able to tell which division it is looking at before it can read any of the other fields.

What each field is

FieldMeaning
opcodeThe operation code. Tells the processor what category of instruction this is — and therefore which of the three divisions to apply.
rsA source register.
rtA second source register in R-type; the target (destination) in most I-type instructions.
rdThe destination register. R-type only.
shamtShift amount. Used only by shift instructions, which arrive in Week 6 — in every instruction you encode this week it is 00000.
functThe function code. Picks the exact operation among R-type instructions, which all share one opcode.
immediate / addressA 16-bit constant (I-type) or a 26-bit target (J-type).
Why a register field is exactly 5 bits

25 = 32, and there are 32 registers. The field width is the logarithm of the register count, and it could not be anything else.

That is not a coincidence and it is not free. Had MIPS chosen 64 registers, every register field would need 6 bits, R-type would need three of them plus an opcode plus a funct code, and the format would no longer fit in 32 bits. The number of registers a processor has is constrained by the shape of its instructions, and the two were designed against each other.

Why every R-type shares the opcode 000000

It looks wasteful: nine instructions all identified the same way, with the real distinction pushed to a field at the far end. It is the opposite.

Every R-type does the same shape of thing — take two registers, compute something, put the answer in a third. So they can all share one decode path in the hardware, and only the ALU's operation select differs between them. Meanwhile the 6-bit opcode space, which is only 64 values wide, stays free for the I- and J-type instructions that genuinely need to be told apart early.

One opcode, one decode path, many operations. You will build the circuit this pays for in Week 11.

Encoding, all the way through

Take sub $s0, $t8, $t9. Its syntax is sub $rd, $rs, $rt, so $s0 is the destination and $t8, $t9 are the sources.

sub $s0, $t8, $t9
It is R-type, so the fields are opcode, rs, rt, rd, shamt, funct.
opcode = 000000 — every R-type.
rs = $t8 = register 24 = 11000 in 5 bits.
rt = $t9 = register 25 = 11001.
rd = $s0 = register 16 = 10000.
shamt = 00000 — not a shift instruction.
funct = 100010 — the code for sub, from the table below.
Assembled: 000000 11000 11001 10000 00000 100010

Two things to notice. $t8 is register 24, not 18 — the $t registers are not contiguous, and that is the single most common lookup error in this material. And the operands in the assembly are written destination first while the fields are laid out sources first, so you cannot copy them across in order.

Decoding, and the order it has to happen in

Going the other way is not symmetric, and the asymmetry is the whole method.

You cannot split the bits until you know the format

Given 32 bits, you do not know where the boundaries are. Bits 6–10 might be rs, or they might be the first five bits of a 26-bit address. The only field whose position is the same in all three formats is the opcode.

So: read the first six bits. Then decide where everything else is.

  • 000000 → R-type. Read the last six bits (funct) to find out which operation.
  • 000010 or 000011 → J-type. Everything after the opcode is one 26-bit address.
  • anything else → I-type. Two 5-bit registers, then a 16-bit immediate.
101011 11101 01000 0000000000010000
Opcode first: 101011. Not 000000, not a jump — so I-type, and the table says sw.
Now the boundaries are known: 6, then 5, then 5, then 16.
rs = 11101 = 29 = $sp.
rt = 01000 = 8 = $t0.
immediate = 0000000000010000 = 16.
sw's syntax is sw $rt, imm($rs), so the answer is sw $t0, 16($sp).

Negative immediates

The immediate field is 16 bits, and for addi, lw, sw, beq and bne it is a signed value in two's complement — the representation you built in Week 1, showing up somewhere new.

addi $v0, $a1, -50: the immediate is 1111111111001110. Read as unsigned, those same bits are 65486. Read as 16-bit two's complement, they are −50. Nothing in the instruction says which reading is right — the opcode does, because addi is defined to sign-extend.

Sign-extended or zero-extended — same field, different rule

These two instructions have identical shapes. Same format, same field positions, same 16-bit immediate:

  • addi $rt, $rs, imm — the immediate is sign-extended to 32 bits. Negative values work.
  • andi $rt, $rs, imm and ori $rt, $rs, imm — the immediate is zero-extended. The top 16 bits are filled with zeros regardless.

Why the difference: arithmetic with a negative constant is ordinary and useful, but a bit mask with its top half set to ones by sign extension would mask the wrong bits. The rule follows what the instruction is for.

Encoding is unaffected — you write the same 16 bits either way. But when you read an instruction and work out what it does, which of these two it is changes the answer, and they are easy to confuse precisely because they look the same.

This week's instruction set

Fifteen instructions. Everything in Assignment 5 comes from this list:

add · sub · and · or · xor · slt · addi · andi · ori · lw · sw · beq · bne · j · jal

The reference tables below carry three more — sll, srl and jr — greyed and marked with the week they arrive. That is deliberate: they are real MIPS instructions and you will meet them, so their absence here should be a signpost rather than a gap. The two shifts are the only instructions that use shamt, and they arrive in Week 6 with the ALU's own shift operations, where the connection between the instruction and the circuit is the point.

You can encode a branch this week without knowing what a branch does

beq and bne are in the list, and you will encode and decode them. What actually happens when a branch is taken — how the program counter gets a new value, how the offset is measured — is Week 7.

That separation is deliberate rather than an oversight. Encoding is a mechanical skill about the shape of an instruction, and it is genuinely independent of what the instruction means. Being clear about which one you are doing is worth something on its own.
