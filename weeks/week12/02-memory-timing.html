Memory Is Slow

Sections 12.5 – 12.8  |  Estimated time: ~45 minutes

12.5   Memory is slower than the processor

Page 1 treated a memory access as instant: the address goes in, the byte comes out. In your Logisim CPU it nearly is. In a real computer it is not. The time from an address arriving to the data being ready is the memory’s access time, and for the main memory in a laptop it is tens of nanoseconds. The processor’s clock cycle is a fraction of one nanosecond. A single read from main memory can take longer than a hundred of the processor’s cycles.

Week 16 shows how caches hide most of that. This page is about the simpler question underneath: if the processor asks and the memory is not ready, what does the bus do?

12.6   Synchronous and asynchronous buses

There are two answers.

A synchronous bus runs everything off one clock, and the memory must deliver by a fixed clock edge. If the memory is too slow for one cycle, the controller adds wait states: extra whole cycles in which the processor simply waits. A memory that needs 45 ns on a bus with a 10 ns cycle needs 5 cycles — the one the access was supposed to take plus 4 wait states. The rule is: cycles needed = access time ÷ cycle time, rounded up; wait states = that number minus 1.

An asynchronous bus has no shared clock for the transfer. It uses a handshake: two control lines, one each way.

  1. The processor puts the address on the bus and raises request.
  2. The memory finds the data, puts it on the bus and raises ready (or acknowledge).
  3. The processor captures the data and drops request.
  4. The memory sees request drop and drops ready. The bus is free.

A fast memory answers quickly and a slow one slowly, and neither side needs to know the other’s speed in advance. Notice the shape: something is raised, the other side answers, the answer is taken, and both are released in order. It is the same nesting as your clock’s set inside enable.

12.7   The memory data register

In Week 9 you traced lw through the multi-cycle MIPS datapath and met a register a program never sees: the MDR, memory data register. Here is why it is there. In that design every cycle ends with every result captured in a register, because in the next cycle the same wires may be doing something else. In cycle 4 of a lw, memory reads the word; in cycle 5 the register file writes it. Between those two cycles, memory’s output is not guaranteed to hold still — its address can change as soon as the next cycle starts. So at the end of cycle 4 the word is captured in the MDR, and cycle 5 writes the register from the MDR, not from memory.

The general rule is the one behind the IR too: when a value arrives in one cycle and is used in a later one, something must hold it in between. The IR holds the instruction; the MDR holds the data.

12.8   Why your CPU has none

Week 9 left this question open: does your CPU need an MDR? It does not, and page 1’s table shows why. In step 5 of LD, RAM_E is high for three quarters, so the RAM drives the bus for the whole of that time, and the destination register’s set pulse sits inside it. The byte is used in the same transfer that it arrives in. Nothing has to survive into a later step, so nothing has to hold it. The destination register is the buffer.

What your CPU does need is that the RAM is fast enough: its byte must be on the bus by the time the set rises, one quarter after the enable. That is the right-hand panel above. In Logisim the RAM answers before your next click, so it always fits; a real build of your CPU would choose the clock so that it did.
