Saying It in MIPS

Sections 6.9 – 6.11  |  Estimated time: ~1.4 hours

You have spent the week building circuits that transform bytes. This page is the other half: the instructions that ask for those transformations by name. Every instruction here corresponds to something you have wired up, and the point of the page is to make that correspondence impossible to miss.

6.9   R-type arithmetic and logic

Last week you met the three MIPS instruction formats. R-type is the one that takes three registers: two to read and one to write. All the instructions in this section share the R-type shape, the opcode field 000000, and are distinguished from each other by the funct field at the bottom.

Each one reads two registers, hands the values to the ALU, and writes the result back to a third register. That sentence is the entire execution model for this section, and the only thing that varies is which ALU leg gets used.

Why does an instruction set bother having nor?

nor is the odd one here. Your ALU has no NOR leg, so the machine has to do an OR and then a NOT — two operations for one instruction. Given that, why does MIPS define it at all?

Because of what it can do with $zero. nor $t1, $t0, $zero computes NOT(t0 OR 0), which is just NOT t0 — and MIPS has no NOT instruction. Rather than spend an opcode on a dedicated NOT, the designers included NOR and let it cover both jobs. One instruction, two uses, one fewer opcode consumed.

That is a recurring theme in instruction-set design, and it is worth noticing while the example is small: the instruction set is not a list of the operations the hardware has. It is a set of choices about which combinations are worth naming.

6.10   slt, and the flag that already exists

slt is "set on less than." slt $t2, $t0, $t1 puts 1 into $t2 if $t0 is less than $t1, and 0 otherwise.

It looks like the most complicated instruction on this page. It is the simplest, and that is the point of this section.

Your machine already computes this. It has been computing it all week.

The comparator leg you built on page 2 produces AL — "A is larger than B" — and it produces it continuously, on every input, regardless of which opcode is selected. It is one of the three status flags.

slt $t2, $t0, $t1 asks whether $t0 < $t1, which is the same question as whether $t1 > $t0. Put $t1 on the ALU's A input and $t0 on B, and the answer is AL, already sitting on a wire. Widen that one bit to a full word — seven zeros and the flag — and write it to $t2.

A whole MIPS instruction, answered by a single wire coming out of a circuit you built on Tuesday.

This is worth sitting with, because it is what an instruction set actually is. slt is not a capability the hardware was given in order to support it. The hardware could already compare; slt is the name by which a program asks for the answer. Somebody designing MIPS looked at what the datapath could already tell them and decided which of those things deserved an instruction.

Notice what is not true here: the answer does not come out of the ALU's 8-bit output. It comes out of a flag. Every other instruction on this page reads the result; slt reads a status bit and ignores the result entirely. Widget 6 draws that difference rather than describing it.

Where this goes

MIPS has no "branch if less than" instruction. The way you write if (x < y) in MIPS assembly is slt followed by beq or bne against $zero — compute the comparison into a register, then branch on whether that register is zero. That is Week 7, and it is the reason slt is taught here rather than alongside the branches.

6.11   The same field, treated two ways

Every instruction so far has taken its operands from two registers. Often what you want is a register and a constant — add 4 to a pointer, mask off the low byte, test a value against a limit. Loading the constant into a register first works, but it costs an instruction every time, and constants are common enough that MIPS gives them their own instruction format.

These are the I-type arithmetic and logic instructions, and they follow a naming convention that makes them easy to read: the R-type mnemonic with an i on the end.

All four have the identical shape: a 6-bit opcode, two 5-bit register fields, and a 16-bit immediate. Same format, same field, same width. But the ALU works on full-width values, so that 16-bit field has to be widened before it can be used — and here the four instructions split into two camps.

Two different ways to widen the same 16 bits, and the instruction decides which

Sign-extension — used by addi and slti. Copy the immediate's top bit into every new position. A 16-bit 1111111111111011 becomes a 32-bit value that is still −5.

Zero-extension — used by andi and ori. Fill every new position with 0. The same 16 bits become 65,531.

Same bits in the same field of the same format, and two instructions read them as a small negative number while two others read them as a large positive one.

The reason is not arbitrary, and it is worth knowing rather than memorising

addi and slti are arithmetic. Their immediate is a number, and numbers have signs. Adding −5 has to mean adding −5, so the value must survive being widened — and sign-extension is precisely the operation that preserves a two's-complement value at a greater width.

andi and ori are bitwise. Their immediate is a mask, and a mask is not a number at all — it is a pattern saying which bits to keep and which to clear. There is no such thing as a negative bit mask. Sign-extending 0x00FF would be fine, but sign-extending 0xF000 would silently set sixteen bits you never asked for, and your mask would stop being your mask.

So the rule is not "remember which two do which." It is: extension preserves whatever the field was meant to be. A number keeps its value; a pattern keeps its shape.
