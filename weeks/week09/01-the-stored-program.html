The Stored Program

Sections 9.1 – 9.4  |  Estimated time: ~1 hour

9.1   You have been the control unit

What you have. A register that holds a byte and lets go of a shared wire (Week 5). An ALU that computes seven things at once and hands back the one you select (Weeks 6–7). A RAM that turns an 8-bit address into one selected byte, with an MAR to hold the address (Week 8). And on the software side, MIPS programs that compute, branch, call procedures and walk arrays.

What you cannot do yet. Make those parts do anything on their own. Think back over what actually moved a value in your circuits. In Week 5, a byte crossed the bus from R1 to R2 because you raised R1’s e, then R2’s s, then dropped them in the right order. In Week 8, a byte reached RAM because you set the address, pulsed sa, and then pulsed s. Every one of those signals came from your mouse. You have been the control unit.

A processor does this hundreds of millions of times a second, and nobody is clicking. Something inside it has to decide, every clock cycle, which line goes high. And it has to get its instructions from somewhere.

What you can do by the end of this week. Describe the organization almost every computer since the late 1940s has shared, and follow a single MIPS instruction through a real processor, cycle by cycle, naming which register changes in each. Building the part that decides is Weeks 10 through 13. This week is about understanding what it will have to do.

9.2   One memory for both

The earliest electronic computers were programmed by rewiring them. ENIAC, completed at the end of 1945, was set up for a new problem by moving cables and setting switches — the program was the wiring. In the same year, John von Neumann’s First Draft of a Report on the EDVAC, written with the ENIAC team’s ideas in front of him, described the alternative almost every computer since has used:

The stored-program idea

Encode the instructions as numbers, and keep them in the same memory as the data they work on. Then changing the program means changing the contents of memory, not the machine — and a program is just another thing a computer can read, write, load and copy.

A machine organized this way is called a von Neumann machine, and it has five parts:

  • Memory holds the program and the data, side by side, as numbers.
  • The ALU does the arithmetic and logic.
  • Control fetches instructions from memory, works out what each one asks for, and drives every other part’s control lines to do it. It is the part you have been playing.
  • Input and output connect the machine to the world.

The ALU, control and a set of registers together are what we call the CPU. One register in that set matters more than the rest this week: the program counter, which holds the address of the next instruction.

The cost: one path

Because instructions and data live in the same memory and reach the CPU along the same path, the CPU can fetch an instruction or move a piece of data, but not both at the same moment. As processors got faster than memory, that single path became the limit on how fast a program could run, and it has a name: the von Neumann bottleneck. It is a real cost of a good idea, and a large part of modern processor design — caches especially — exists to work around it. You will see how in Week 16.

The other arrangement

A Harvard machine keeps instructions and data in two separate memories with two separate paths. Many small microcontrollers are built that way, and you will meet a textbook MIPS design that is too, in Week 11. Everything on this week’s pages is the von Neumann arrangement: one memory.

9.3   An instruction is a number

Here is the program this week follows. It adds up a three-element array and stores the total. Every instruction in it is one you have written before.

.data vals: .word 6, 11, 8 # 0x10010000, 0x10010004, 0x10010008 sum: .word 0 # 0x1001000C .text la $s0, vals # a pseudo-instruction: two real words, 0x00400000-0x00400004 addi $t0, $zero, 3 # $t0 = how many are left add $t1, $zero, $zero # $t1 = the running total loop: lw $t2, 0($s0) # the next element add $t1, $t1, $t2 addi $s0, $s0, 4 # point at the next word addi $t0, $t0, -1 bne $t0, $zero, loop sw $t1, 0($s0) # $s0 now points at sum addi $v0, $zero, 10 # exit syscall

Assemble it in MARS and look at the Execute tab. The Text Segment pane shows each instruction as a 32-bit word at an address starting from 0x00400000 — the encodings you learned to build by hand in Week 5. The Data Segment pane shows 6, 11, 8 and 0 as 32-bit words starting from 0x10010000. Different addresses, the same memory, the same kind of thing: 32-bit numbers.

So try reading each one the other way.

Two of the data words deserve a second look. The 0 stored at sum is also sll $zero, $zero, 0: shift register zero left by nothing and put the result in register zero, which can never change. It does nothing, and that is exactly what MIPS uses it for: MIPS gave “do nothing” no opcode of its own, and MARS assembles nop to this same all-zero word. And the 8 at vals[2] is jr $zero — a jump to address 0. As data it is a small number in an array. As an instruction it would send the program somewhere it has no business going.

9.4   What decides: the PC

Nothing in a word marks it as an instruction or as data. The machine decides by how it reaches the word:

  • A word is an instruction if the PC points at it. Fetch reads it into the processor and decodes it.
  • A word is data if a load or store points at it. It is copied to or from a register and never decoded.

That is the Week 1 idea at full size. Week 1’s byte 01000010 was 66, or the letter B, or part of an instruction, depending on what the program did with it, and its page promised that this week you would see the last of those readings in action. Here it is: the same 32 bits are an addi if the PC lands on them and a large integer if a lw does.

It also explains a whole family of bugs. If a branch target is computed wrongly, or a procedure returns through a corrupted $ra, the PC can end up pointing at data — and the machine will fetch it, decode it and execute it, because it has no way to know it should not. A procedure that forgets to save $ra before calling another, as in Week 7, sends the PC somewhere unintended too — usually back into its own code, which is the mild version.
