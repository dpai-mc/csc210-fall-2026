The Language the Bytes Turn Out to Be

Sections 5.5 – 5.6  |  Estimated time: ~1.5 hours

5.5   Why a Processor Needs a Language

You now have a circuit that holds a byte and hands it over when asked. Eight bits, stored, retrievable, and connectable to other circuits that do the same.

Here is the thing that circuit cannot tell you: what the byte means.

Week 1, collected on

In the first week of this course you met an idea and were probably not sure yet what to do with it: a single byte can be an integer, a character, a colour channel, or part of an instruction — and context decides which, not the bits themselves.

Three of those four have come up since. This is the week the fourth one stops being hypothetical.

Your register holds 01000001. Is that the number 65? The letter A? A shade of dark red? A piece of an instruction telling the processor to add two things together? Nothing in the circuit knows. The wires carry voltages and the cells hold whatever they were told to hold.

So something outside the circuit has to supply the meaning — an agreement about which bit patterns stand for which operations, which registers, which addresses. That agreement has a name.

The ISA is a contract

An Instruction Set Architecture is the abstract interface between hardware and software. It defines everything a programmer needs in order to write correct machine code — the instructions that exist, the registers available, how memory is addressed, what the data types are — without saying anything about how the hardware implements any of it.

It is worth dwelling on the word contract, because the analogy is not decorative. A contract has two sides, both sides depend on it, and neither side gets to change it alone.

  • The software side promises to produce only bit patterns the contract defines, in the shapes the contract specifies.
  • The hardware side promises that any such pattern will do what the contract says it does.
  • Neither side promises anything else. The compiler does not know how many gates are in the adder. The processor does not know what language your program was written in.
What the contract buys, concretely
  • A program compiled in 1999 still runs. The hardware underneath has been redesigned a dozen times; the contract has not.
  • Two processors from different companies run the same binary. They share no circuitry at all. They share a contract.
  • Your CPU will need one. Before the final project, you will define a small instruction set of your own — which bit patterns your machine recognises and what each one makes it do. You are reading about MIPS partly to have seen a real one first.

Two philosophies

Designing an ISA means deciding how much work a single instruction should do. There are two long-standing answers, and the argument between them shaped every processor you have ever used.

RISC — Reduced Instruction Set ComputerCISC — Complex Instruction Set Computer
Goal: make the hardware simple and fast. Goal: make programming easier with powerful instructions.
Simple, fixed-length instructions. Variable-length, complex instructions.
Most instructions execute in a single clock cycle. An instruction may take many cycles to complete.
A strict load/store architecture — only two instructions touch memory. Many different instruction types can reach memory directly.
Complexity moves to the compiler, which combines simple instructions. Complexity stays in the hardware, which decodes multi-step instructions.

Neither is a mistake. They are different bets about where complexity is cheapest to put, made at different times under different manufacturing constraints.

MIPS is RISC, and one consequence matters more than any other this week:

Every MIPS instruction is exactly 32 bits

Not "usually 32." Not "between 1 and 15 bytes depending on what it is." Every single one, always, exactly 32 bits.

That is not an arbitrary fact to memorise — it falls directly out of the RISC bet. Fixed width means the processor knows where the next instruction starts before it has finished reading this one, which is what makes the decoding hardware simple enough to be fast.

It is also what makes the next page possible at all. You are about to encode instructions into binary by hand, and that is a tractable exercise precisely because there are exactly 32 slots to fill, every time.

Optional: what the other bet looks like — MIPS and x86 side by side

This aside assumes only that you are willing to read four lines of unfamiliar assembly. No prior assembly experience, nothing from another course. It is here because seeing the contrast makes the RISC/CISC distinction concrete rather than abstract. Skipping it costs you nothing — nothing in Assignment 5, the Midterm, or any later week depends on having read it.

Intel's x86 is the classic CISC architecture. Here is the same small task in both: load two numbers from memory, add them, store the result back.

MIPS (RISC)

# $s0 holds the base address
lw   $t0, 0($s0)     # load varA
lw   $t1, 4($s0)     # load varB
add  $t2, $t0, $t1   # add them
sw   $t2, 8($s0)     # store the sum

Four steps. Two loads, one operation, one store. All arithmetic happens on registers — nothing else can touch memory.

x86 (CISC)

; EBX holds the base address
mov eax, [ebx]       ; load varA
add eax, [ebx+4]     ; add varB FROM MEMORY
mov [ebx+8], eax     ; store the sum

Three steps. The add reads an operand straight out of memory, folding a load and an operation into one instruction.

Three structural differences follow from that one example:

  • Instruction length. MIPS: fixed at 32 bits, three formats, consistent field positions. x86: variable, from 1 to 15 bytes, which makes decoding a multi-step process the hardware has to do before it can even find the next instruction.
  • Memory access. MIPS is load/store — data must be in a register before you can compute with it. x86 allows memory operands in many instruction types.
  • Registers. MIPS has 32, largely interchangeable. Classic 32-bit x86 has 8, several with specialised historical roles (EAX the accumulator, ECX the counter), which makes a compiler's job of allocating them harder.

Where this comparison breaks — and these matter:

  • This is 32-bit x86, and the course's recommended text is x86-64. Plantz's Introduction to Computer Organization covers x86-64, where the registers are named RAX rather than EAX, there are sixteen of them rather than eight, and the calling convention is different. If you read Plantz alongside this aside, expect the names not to match.
  • "CISC is simpler for the programmer" is a design intention, not a measured result. It was the goal. Whether it was achieved is a genuinely contested question, and almost nobody writes x86 by hand any more — compilers do, and compilers do not find powerful instructions easier.
  • The clean dichotomy above is partly historical. Modern x86 processors decode those complex instructions internally into simpler, RISC-like micro-operations and execute those. So the contract is CISC and the machine underneath is closer to RISC — which is, if you think about it, the ISA-as-contract idea working exactly as advertised: the hardware changed completely and the contract did not.

5.6   The MIPS Register File

A MIPS processor contains 32 registers.

Before any of them get names, be clear about what one of them is: it is the circuit you built this week. Not something analogous to it, not something that plays a similar role. Storage cells in parallel under a shared write control, read out through an output stage that can stop driving so the value can be put on a shared wire. The same device.

One difference, and it is only the count
What you built: 8 bits

Eight MEM_1BIT cells on one s line. This is what your CPU uses, what Checkpoint 1 grades, and what every circuit from here to Week 17 assumes.

A MIPS register: 32 bits

Thirty-two cells on one write line. This is what $t0 is, and what every instruction format on the next page assumes.

What changes when you widen it: the number of cells, and nothing else. Same construction. Same two controls — one to write, one to drive the bus. Same reason the output stage needs to be able to let go. The splitter fans out to thirty-two wires instead of eight; the write line reaches thirty-two cells instead of eight.

A 32-bit register is a wider 8-bit register. It is not a different device.

And the reason this course is 8-bit: Logisim Classic 2.7.1 becomes unusably slow with a 32-bit datapath wired up, and everything interesting about a register is already visible at 8. The width is a practical limit on the simulator, not a simplification of the idea.

The names, and what they are for

All 32 registers are, at the hardware level, identical. The names below are conventions — agreements about who uses what for what — and they exist because assembly code written without them is unreadable and uncombinable.

The hardware does not enforce any of this

$t0 and $s0 are registers 8 and 16, and the processor treats them identically. There is no circuit anywhere that makes a "temporary" register behave differently from a "saved" one.

The difference between them is an agreement between programs: if you call a procedure, it may freely overwrite the $t registers and must put back anything it changes in the $s registers. Break the agreement and nothing catches you — your program simply produces wrong answers in a way that is very hard to find.

Which makes this the same kind of object as the ISA itself. A convention held up by everyone obeying it. You will use this one seriously in Week 7, when procedures arrive and the stack has to be managed.

$zero is the exception, and it is real hardware

Register 0 reads as 0, always. Writes to it are discarded — not an error, just silently dropped. That is wired in, not agreed.

Spending one of your 32 registers on a constant sounds wasteful until you count how often you need it. Comparing something against zero; clearing a register; copying a value from one register to another, which is just add $t1, $t0, $zero — a processor that has a hardwired zero does not need separate instructions for any of those. One register pays for several.

The two halves of this week, in one instruction

Take the instruction add $t0, $t1, $t2.

Three registers are named. Two of them are read — their stored bytes are driven onto internal wires. One is written — the result is put on its input and its write line is raised. The others sit there holding what they hold, driving nothing.

Every one of those actions is something you built a circuit for this week. Reading a register is raising its e. Writing one is raising its s. And the reason exactly one register drives at a time is the reason its output stage can stop driving at all.

And the choosing? Picking one of 32 registers from a 5-bit number is a decoder — the circuit you built in Week 3, when you were told it would matter later. This is later. In Week 10 you will wire the decoders that select between R0, R1, R2 and R3, and they are the same component at a smaller width.

There is no second mechanism. $t0 is a register, a register is eight cells and two control lines, and a cell is four NAND gates. It is turtles most of the way down, and then it is gates.

Self-check
Three questions, not graded, no record kept. The third one is the one worth getting right.
1. You need a value to survive a call to another procedure. Which group of registers should it be in?
2. What happens if a program executes addi $zero, $zero, 5?
3. A MIPS register is 32 bits and the register you built is 8. What is different about how the wider one is constructed?
