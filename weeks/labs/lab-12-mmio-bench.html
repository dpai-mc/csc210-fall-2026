What This Session Is, and What It Is Not

This lab does not connect your CPU to its RAM. Putting the MAR and the RAM on your CPU’s bus is Week 13’s Checkpoint 6, built from that week’s pages. And it does not add a memory data register: your CPU has none, and page 2 of this week explains why.

What we build here is a device that lives at a memory address — the idea at the centre of page 3, built with your own RAM and one register, so that “a store to this address goes to the screen instead” is something you wired rather than something you read. Then, in MARS, you write a program that talks to a keyboard and a display through addresses alone, and count how much of its time it spends asking.

The Question Today Answers

What you have: A RAM with its MAR from Week 8, a MEM_8BIT from Week 5, and this week’s pages on the memory bus and on memory-mapped I/O (The Memory Bus, Input and Output).

What you cannot do yet: Say what decides whether a store goes to memory or to a device, or what happens when that decision is made carelessly.

What you can do after today: Build an address decoder that steals one address for a device, break it two ways that real computers have shipped with, and write a MARS program that echoes the keyboard to the display by polling.

What You Will Be Able to Do

  1. Map an output device to one address of your RAM’s address space, with a decoder you design.
  2. Break the address decoding two ways, and explain aliasing and shadowing.
  3. Write a polling program for MARS’s keyboard and display, from a specification.
  4. Measure polling’s cost in your own program, and compare it with syscall.

Part 2 — Build MMIO_BENCH ~17 minTogether

One RAM, one 8-bit register called DISPLAY, and an address decoder that watches the address. When the address is 0x1F — the last populated byte of your RAM — a write goes to DISPLAY instead of to memory. Everywhere else, nothing changes. That is all memory-mapped I/O is.

  1. Place one RAM_16X16 instance. Input pins address and data (8 bits) to its address and i. Tie its sa to a constant 1, so the MAR simply follows address, and its reset to a constant 0. Its o to an 8-bit output pin o.
  2. Place one MEM_8BIT instance, labelled DISPLAY. Its i from data; its o to an 8-bit output pin display.
  3. Design the address decoder: an output io that is 1 when address is exactly 00011111 and 0 for every other address. Split the address into its eight bits; you need one gate with eight inputs, and some NOTs. Bring io out to an output pin.
  4. Input pins wr and rd. Three AND gates: wr AND NOT io into the RAM’s s; rd AND NOT io into the RAM’s e; wr AND io into DISPLAY’s s. Every input pin pull-down.
Open if your decoder will not come out right: the gate

0x1F is 0001 1111: bits 7, 6 and 5 are 0 and bits 4 to 0 are 1. One AND gate with eight inputs: bits 4, 3, 2, 1 and 0 straight in, bits 7, 6 and 5 through NOT gates. It is one row of the DECODER_4TO16 idea, done for all eight bits at once.

How to store and load on this bench

Store: set address and data first, then pulse wr. Load: set address, raise rd, read o, drop rd. Never change address while wr is high: with sa tied to 1 the MAR follows it, which is the Week 8 hazard.

Part 3 — Six Accesses ~8 minYour own, then compare

2
Store, store, store, load, load, store

In order, recording io, display and o after each, and whether any RAM byte changed (look inside the RAM instance, or load it back):

  1. Store 0x41 at 0x05.
  2. Store 0x48 at 0x1F.
  3. Store 0x69 at 0x1F.
  4. Load from 0x05.
  5. Load from 0x1F.
  6. Store 0x21 at 0xFF.

Which of the six reached a device, which reached memory, and which reached nothing at all?

Part 4 — Break the Decoder ~12 minYour own, then compare

Compare With the Room — before break A

A cheaper decoder looks only at bits 4 to 0, and ignores bits 7, 6 and 5. With that decoder, where does a store of 0x21 at 0xFF go? Everybody answers before anyone rewires.

A
Partial decoding

Disconnect bits 7, 6 and 5 from your decoder’s AND gate (a five-input AND of bits 4 to 0). Repeat access 6: store 0x21 at 0xFF. Then store 0x7E at 0x3F. Record display both times.

How many different addresses now reach DISPLAY? List them in hex.

B
Forget to block the memory

Restore the full decoder. Now wire the RAM’s s straight from wr and its e straight from rd, leaving out NOT io. Store 0x5A at 0x1F, then load from 0x1F. Record display and o.

A program that writes to the screen and then reads the same address back — what does it get, and where did it come from?

Open after you have recorded both breaks: the names for what you saw

Break A is aliasing. A decoder that ignores some address bits answers to every address that matches on the bits it does look at: with three bits ignored, eight addresses all reach the same device. Early home computers often decoded this way to save gates, and their manuals listed the “mirror” addresses.

Break B is a shadow. The store reached both the device and the RAM byte underneath it, so a later load reads memory’s copy and the program believes it read the device. A memory-mapped device has to take its address from memory, not share it.

Restore the full decoder and the NOT io inputs before you submit.

Part 5 — MARS: Echo the Keyboard ~40 minYour own

You write this program; nobody hands it to you. Page 3 showed a program that prints a fixed string by polling the display. Yours reads from the keyboard too.

3
The specification
  1. Wait for a key: poll the receiver control register until its ready bit is 1. Count every poll that finds it not ready, in a register you choose.
  2. Read the character from the receiver data register.
  3. If the character is . (period, ASCII 46), stop echoing.
  4. Otherwise wait for the display: poll the transmitter control register until ready, then store the character in the transmitter data register. Count the characters echoed.
  5. Repeat from 1.
  6. After the period: using syscall, print the number of characters echoed, a newline, and the number of not-ready keyboard polls; then exit.

Save it as lab12_yourname.asm. Comment every line that touches a device register.

Reference card receiver control 0xffff0000 bit 0 = 1: a key is waiting receiver data 0xffff0004 the key, low byte; reading it clears the ready bit transmitter control 0xffff0008 bit 0 = 1: the display is ready transmitter data 0xffff000c store a character here to show it li $s0, 0xffff0000 MARS expands this into two instructions lw $t0, 0($s0) andi $t0, $t0, 1 beq / bne syscall: 1 print integer ($a0) 11 print character ($a0) 10 exit Rules: .data before .text if you have one; no main:, no .globl
4
Run it
  1. Assemble. Open Tools → Keyboard and Display MMIO Simulator and click Connect to MIPS.
  2. Run. Click in the tool’s lower box (the keyboard) and type hello. at your normal speed. Each letter should appear in the upper box (the display).
  3. Record what the console prints. Run it again, typing hello. as fast as you can, and record the counts again.

If nothing appears, check that the tool says it is connected, and press its Reset button between runs.

Three questions — answer them in comments at the end of your .asm

Q1
What polling cost

How many not-ready polls did each run make, for six keys? Divide by the characters echoed. Why did typing faster change the count, and what was the processor doing the rest of the time?

Q2
Your store, on your bench

Your sw to 0xffff000c is MARS’s version of which access in Part 3? What, in MARS, plays the part of your io decoder?

Q3
What syscall hides

Rewrite the echo step with syscall 11 instead of the transmitter registers, in a comment. What do you no longer write, and on a real computer, who does that work instead (page 4)?
