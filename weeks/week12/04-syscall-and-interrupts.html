12.13   Programs that need help

Page 3’s program wrote straight to the display. On a real computer an ordinary program is not allowed to: the device registers belong to the operating system, which shares the screen, the keyboard and the disk among every program running, and checks that each request is allowed. The processor enforces this with two modes. In kernel mode the operating system can touch anything; in user mode a program that tries to reach a device register, or the operating system’s memory, is stopped. So a user program needs a way to ask the operating system to do something for it — a way that also switches the processor into kernel mode, safely, at a place the operating system chose.

You have been using that way since Week 5. It is syscall.

12.14   syscall is a software interrupt

Week 5 taught the calling side: put a service number in $v0, any arguments in $a0 and $a1, and execute syscall; a result, if any, comes back in $v0. These are the services this course uses:

Here is what the hardware does with it. syscall is an instruction whose whole job is to cause an exception — a deliberate one, which is why it is called a software interrupt or trap. When it executes, a MIPS processor:

  1. saves the address of the syscall in a special register, EPC (exception program counter), so it knows where to come back to;
  2. records the reason in the Cause register — code 8 means “system call”;
  3. switches to kernel mode and sets the PC to a fixed address where the operating system’s exception handler lives (0x80000180 in MARS);
  4. the handler reads $v0, performs the service — talking to the device registers itself — and puts any result in $v0;
  5. the handler returns to the instruction after the syscall, back in user mode.

Look at what that is: the PC is changed to an address the program did not choose, after the old address is saved. It is a jump, made by the hardware, to the operating system. MARS has no operating system, so it performs each service itself and moves straight on; the program sees the same result either way.

    12.15   Hardware interrupts

    Page 3 ended with polling’s cost: a program asking “ready yet?” over and over. An interrupt turns the question round. The device gets a wire to the processor, and raises it when it is ready — a key has been pressed, a disk block has arrived. Between instructions the processor checks that wire; if it is up, it does exactly what it does for syscall: saves the PC in EPC, records the cause (this time “a device”), and jumps to the handler. The handler deals with the device and returns, and the interrupted program carries on as if nothing had happened.

    So there are three kinds of event and one mechanism. A hardware interrupt comes from a device, at any moment. A software interrupt — syscall — comes from the program, on purpose. An exception in the narrow sense comes from a mistake, such as an arithmetic overflow or an address that is not aligned; MARS reports those as runtime errors. All three save where the program was and jump to the operating system. The trade-off against polling: interrupts let the processor do useful work while a device is busy, at the price of saving and restoring state on every event. A device that is almost always ready, or a program with nothing else to do, may as well poll.

    The MARS display can interrupt too: setting bit 1 of its control register asks it to. Using that needs an exception handler of your own, which is beyond this course.

    12.16   Your CPU, and Phase 3 in one picture

    Your CPU has none of this machinery: no kernel mode, no EPC, no interrupt wire, no syscall. When its program is finished, the END instruction (Week 10) will stop its clock — you build the circuit that detects it in Week 14. That is a fair place for a teaching CPU to stop; everything on this page is built on top of the fetch-decode-execute loop you now understand, by adding a few registers and one more way to change the PC.
