Pipelining, and Why It Is Hard

Sections 15.9 – 15.12  |  Estimated time: ~45 minutes

15.9   Overlap

Your CPU finishes one instruction completely before it starts the next. While it is executing an ADD, the hardware that fetched that ADD is doing nothing, and while it fetches, the ALU is doing nothing. Page 2 ended with the question of how a processor can do more work in each cycle. The main answer is to keep every part busy all the time, on different instructions.

Split the work of an instruction into k stages, each done by its own hardware, with a register between one stage and the next to hold what it has produced. A generic four-stage design:

StageDoes
F — Fetchreads the instruction at the PC from memory, adds to the PC
D — Decodedecodes it and reads its registers
X — Executethe ALU computes the result (or the address, or the branch decision)
W — Write backwrites the result to a register

Each cycle, every instruction in the pipeline moves on one stage, and a new one enters at F. One instruction still takes four cycles from start to finish: its latency is unchanged. But once the pipeline is full, one instruction finishes every cycle: the throughput is four times higher. n instructions take

one at a time: k × n cycles pipelined: k + n − 1 cycles (k to fill, then one per cycle)

For a long program the CPI gets close to 1, whatever k is, and each stage does less, so the clock can be faster too. That is how pipelining pulls two levers at once.

An analogy: the laundry

This assumes you have done laundry with a separate washer and dryer. Skip it if not: nothing above or below depends on it.

Four loads, each needing the washer, then the dryer, then folding. Done one load at a time, the washer sits idle while the first load dries. Start the second load washing the moment the first moves to the dryer, and all three stations work at once: each load takes as long as before, but the last load is folded much sooner.

Where the analogy breaks
Loads do not depend on each other
Instructions do. If the second instruction needs the first one’s result, it cannot start its work on time (15.11). No load of laundry needs another load to be dry first.
You always know the next load
A processor does not, after a branch: it has to fetch the next instruction before it knows which one comes next (15.12).
The stations are equal
Pipeline stages rarely are, and the clock has to suit the slowest stage.

15.10   Why your CPU cannot do this

Every one of your CPU’s six steps is a transfer over the one bus. To fetch the next instruction while executing this one, the PC would have to drive the bus in the same step as a register does: two values on one wire. Week 5 taught what that is. When two instructions need the same piece of hardware at the same time it is a structural hazard, and the single bus makes every pair of steps one.

Pipelined processors remove it by giving every stage its own hardware: separate paths instead of one bus, a register file that can read two registers and write one in the same cycle, and separate places to fetch instructions and data from. That is a large part of their cost. Your CPU’s single bus is the simplification that made it something you could build and debug in a semester (Week 10), and this is what it gives up.

15.11   Data hazards

Even with all that separate hardware, overlap breaks down when one instruction needs another’s result:

add $t0, $t1, $t2 # writes $t0 in W sub $t3, $t0, $t4 # reads $t0 in D

One at a time this is no problem. In a pipeline, sub reaches D, where it reads its registers, one cycle behind add, before add has reached W. If it read $t0 then, it would get the old value. So it has to wait in D until add writes. (This design writes registers early in a cycle and reads them late, so a value written in W can be read in D in that same cycle.) The wasted cycle is a stall, also called a bubble, and everything behind sub waits too. This is a data hazard.

Look at the shape of it: the result of one step is needed by the next, and the next cannot start until it arrives. It is Week 6’s ripple carry, one level up, between instructions instead of between bits. Week 16 shows how processors avoid most of these stalls by passing a result straight from the ALU to the next instruction instead of waiting for it to be written.

15.12   Control hazards

A branch is the other dependency: which instruction comes next depends on the branch’s result. In the four-stage pipeline the branch decides in X, but by then F has already fetched the two instructions after it, assuming the program would carry straight on. If the branch is taken they are the wrong instructions: they are thrown away before they write anything, fetching restarts at the target, and those cycles are lost. This is a control hazard, and the third program in the chart shows it.

Your CPU has the same question, in its own form: a Jcaez only knows at step 6 whether it is taken. In MYSIM.txt the JC is taken 3 times out of 16. A pipeline that simply guessed “not taken” every time would be right 13 times in 16 and pay only for the other three. Guessing well is called branch prediction, and it is one of the things Week 16 covers.

Week 6’s promise, kept

Carry-lookahead breaks the dependency between the bits of a sum. Pipelining breaks the dependency of one instruction waiting for the previous one to finish. Stalls, forwarding and branch prediction are how a pipeline copes with the dependencies it cannot break. Every technique on these two pages is an attempt to break a dependency, or to work around one it cannot break.
