5.8   MARS: A Program That Runs

Everything so far this week has been on paper or on a canvas. This page is where it executes.

The tool

MARS — the MIPS Assembler and Runtime Simulator. You installed it in Lab 1 and have not touched it since. It does four things:

  • An editor for writing assembly.
  • An assembler that turns your assembly into the 32-bit instructions you spent the last page encoding by hand.
  • A simulator that executes them, all at once or one at a time.
  • Live panes showing every register and every byte of memory as it changes.

That last one is why this page exists. You have built a register and you have argued that $t0 is one. Now you get to watch thirty-two of them.

The program

Six instructions and one variable. Type it rather than pasting it — the typing is where the syntax sticks.

.globl main # make main visible as the entry point .text # everything below here is code main: li $t2, 25 # load the constant 25 into $t2 lw $t3, value # load the word stored at 'value' into $t3 add $t4, $t2, $t3 # $t4 = $t2 + $t3 sub $t5, $t2, $t3 # $t5 = $t2 - $t3 li $v0, 10 # syscall code 10 means "exit" syscall # hand control back to the system .data # everything below here is data value: .word 12 # a 32-bit integer, initialised to 12

The three directives

Lines beginning with a dot are not instructions. They are directives — messages to the assembler about how to lay the program out, rather than things the processor executes.

DirectiveWhat it does
.text Everything after this is code. The assembler puts it in the part of memory where instructions live.
.data Everything after this is data. Variables, constants, strings.
.globl main Makes the label main visible outside this file, so the system knows where to start.
Leave out .globl main and things get strange

Some simulators start at the first instruction regardless and it appears to work. Others refuse to run at all. Neither is a bug — without .globl you have not said where the program starts, so the behaviour is whatever that particular tool does about it.

Write it. It is one line, it is what every real MIPS program has, and the failures it prevents are the confusing sort.

Comment every executable line

Not a style suggestion — a course expectation, and it is graded. A comment starts with # and runs to the end of the line.

The reason is specific to assembly rather than general good practice. A line of C says what it is doing. A line of MIPS says what the processor is doing, which is often three steps removed from what you are doing. add $t4, $t2, $t3 is perfectly clear about adding two registers, and tells you nothing about why. Six months from now — or on Wednesday — the comment is the only record of the intent.

What each instruction does

li $t2, 25 # load the constant 25 into $t2

Load immediate. Puts a constant straight into a register. After this line, $t2 holds 25.

li is not a real instruction

Go back to the three formats on the previous page and try to find li in them. It is not there, and it is not in the reference tables either.

It is a pseudo-instruction — something the assembler accepts for your convenience and then translates. li $t2, 25 usually becomes:

addi $t2, $zero, 25

Which is a real I-type instruction, and it works for a specific reason you learned two pages ago: $zero always reads as 0, so adding a constant to it yields the constant. A hardwired zero plus an existing instruction format, and no new hardware needed.

Go and look. MARS shows you the substitution. Assemble the program and look at the listing — the source column shows what you typed and the code column shows what the processor actually gets. It is the clearest demonstration in the course that assembly language and machine code are not the same thing.

lw $t3, value # load the word stored at 'value' into $t3

Load word. Goes to memory, reads 32 bits from the address labelled value, and puts them in $t3. After this line $t3 holds 12.

This is the load half of load/store — the RISC property from two pages back. The value has to come into a register before anything can compute with it. How the address is worked out, and what your own RAM circuit will do about it, is Week 8.

add $t4, $t2, $t3 # $t4 = $t2 + $t3 sub $t5, $t2, $t3 # $t5 = $t2 - $t3

The arithmetic. Both R-type, both taking two registers and writing a third. 25 + 12 = 37 into $t4; 25 − 12 = 13 into $t5.

You can encode both of these by hand now. It is worth doing for one of them, then checking against what MARS produces.

li $v0, 10 # syscall code 10 means "exit" syscall # hand control back to the system

The system call. syscall is a request to the system for something the program cannot do itself. Which service you want goes in $v0 first — 10 is "exit."

A program without this does not end; it runs off the bottom of your code into whatever happens to be in memory next. Always finish with it.

Other useful codes, for when you want output: 1 prints the integer in $a0, 4 prints the string at the address in $a0, 5 reads an integer into $v0. How a syscall actually works — what the hardware does when it sees one — is Week 12.

Run it, and then run it slowly

  1. Open MARS and type the program into a new file. Save it as week5.asm.
  2. Assemble it (Run → Assemble, or F3). Errors appear at the bottom with line numbers; fix them before continuing.
  3. Look at the Text Segment pane. Every line of your program is there with its 32-bit encoding beside it. Find the line that came from li and see what it turned into.
  4. Run it (F5). It finishes immediately and says the program exited.
  5. Now reset (F12) and use single step (F7) instead. One instruction per press.
  6. Watch the Registers pane on the right as you step. Changed values are highlighted.

Look at that pane again

Thirty-two rows. Each one a value that persists until something deliberately changes it, updated when an instruction says to write there and left alone otherwise.

Each row is the circuit sitting in your .circ file. Thirty-two cells wide instead of eight, and otherwise the same device — a shared write line, an output stage that can let go, a byte captured at one moment.

When add $t4, $t2, $t3 executes, two registers put their contents on internal wires and a third one has its write line raised. That is e, e, and s. You built all three this week.

5.9   Synthesis: Two Halves of One Machine

Three new tabs in your .circ file:

  • MEM_8BIT — eight of last week's cells, one write line.
  • ENABLE_8BIT — the output stage that can be silent.
  • REGISTER_8BIT — the component four other things in your finished CPU are copies of.

And a program that assembled, ran, and moved numbers between registers you can name.

The idea worth keeping

Storing a value and putting it where others can see it are two different acts, needing two different controls — and the second one requires a device that can be silent.

Almost everything about how a CPU moves data follows from that. The bus exists because dedicated wires do not scale. Tri-state exists because a bus needs devices that can be absent. The four-step transfer exists because a level-sensitive register is transparent while it is being written. The clock exists because something has to produce those four steps in that order, forever.

Pull any one of those threads and the others come with it.

What happens next

Week 6

A register holds a value. It cannot change one. Next week you build the circuit that can — and every arithmetic instruction you just learned to encode is a request to that circuit.

The ALU. It is built around the 8-bit adder you finished in Week 3, with a decoder from the same week selecting which of seven operations reaches the output — and each of those seven operation paths drives the output through an ENABLE_8BIT, the circuit you built this week. Three weeks of components, wired together into the part of the machine that actually computes.

On the software side, Week 6 is the arithmetic and logic instructions in earnest: what add, sub, and, or and slt do, and writing programs that use them rather than encoding them by hand.

The two tracks stay side by side through Week 8, and then they meet.
