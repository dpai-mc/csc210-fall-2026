7.10   The stack, and the problem it solves

You can call a procedure with jal and return with jr $ra. Try to use that twice and it falls apart immediately.

outer: jal inner # $ra ← back into outer # ... jr $ra # ← where does this go? inner: jr $ra
There is one $ra, and the second jal destroys the first one

When outer was called, $ra was set to the address to return to. Then outer calls inner, and that jal overwrites $ra with the address inside outer. The way back out of outer is simply gone.

The same applies to any register: inner has no idea what outer was keeping in $t0, and will happily use it.

So a procedure needs somewhere to put values that must survive a call. Not a fixed address — a procedure can be called from anywhere, twice over, or by itself, and a fixed address would be overwritten by the second call exactly as $ra was.

What the stack is

A region of memory, and one register — $sp, the stack pointer — holding the address of the top of it. That is all.

It grows downward, so allocating is subtraction

$sp starts high and moves down as things are pushed. To make room for three words:

addi $sp, $sp, -12 # 3 words × 4 bytes

and to give it back:

addi $sp, $sp, 12

The downward direction is a convention, not a necessity — it exists so that the stack and the heap can grow towards each other from opposite ends of memory and neither has to be given a fixed size in advance.

You will meet sw and lw properly in Week 8. For now: sw $ra, 4($sp) stores $ra at four bytes above where $sp points, and lw reads it back.

Every word on the stack is four bytes, and every offset from $sp is a multiple of four. A procedure's chunk of the stack is called its frame.

7.11   The calling convention

Nothing in the hardware enforces any of what follows. These are agreements — between you and the assembler, between your code and library code, between two procedures written by different people. A convention everyone follows is what makes separately written code fit together.

RegistersUsed forWho guarantees it survives a call
$a0–$a3arguments innobody — assume they are destroyed
$v0–$v1results outnobody
$rareturn addressthe callee, if it calls anything
$t0–$t9scratchthe caller — save them yourself if you need them
$s0–$s7values worth keepingthe callee — restore them before returning

Caller-saved and callee-saved sound alike and mean opposite things

Caller-saved — $t0–$t9

The caller saves these if it cares about them. A procedure may use $t registers freely and leave them in any state.

"I am about to call something, so anything I have in a $t is at risk."

Callee-saved — $s0–$s7

The procedure being called saves these if it wants to use them, and restores them before returning. A caller can rely on an $s register surviving.

"If I use an $s, I have to put it back the way I found it."

The word "saved" in both names refers to who does the saving, not to whether the value is safe. That is the whole confusion, and it is worth re-reading the table above with that in mind.

The rule that decides what actually goes in a frame

Save what you would otherwise destroy

Not "always save $ra." Not "always allocate a frame." Work through it:

  • Does this procedure call anything? If yes, jal will overwrite $ra, so save it.
  • Does it use any $s register? If yes, save that one, because the caller is entitled to get it back.
  • Does it need an argument to survive a call it makes? If yes, save that too — $a0 is not protected by anybody.
  • Otherwise? It needs no frame at all.
A leaf procedure using only $t registers needs no stack frame

A leaf procedure is one that calls nothing. It cannot lose $ra, because nothing overwrites it. If it also confines itself to $t registers, it destroys nothing anyone is relying on — so it needs no prologue, no epilogue, and no stack at all. It is just jr $ra at the end.

Three of the four procedures on this week's assignment are in this category. Recognising that is part of knowing the convention, not an exception to it — a procedure that allocates a frame it does not need is not being careful, it is being wrong in a way that happens not to break.

The shape of a procedure that does need a frame

# Example: a procedure that calls something and uses $s0 example: # Prologue — save what we would otherwise destroy addi $sp, $sp, -12 # room for 3 words sw $ra, 8($sp) # we call out, so $ra is at risk sw $s0, 4($sp) # we use $s0, so the caller's must be kept sw $a0, 0($sp) # we need our argument after the call # Body jal something lw $a0, 0($sp) # our argument, back again # Epilogue — restore in REVERSE order lw $a0, 0($sp) lw $s0, 4($sp) lw $ra, 8($sp) addi $sp, $sp, 12 # $sp back exactly where it was jr $ra
Two rules that account for most broken procedures

Restore in the reverse order of saving. Not because the machine requires it — the offsets are explicit, so any order works — but because reading a prologue and epilogue as mirror images is how you spot a missing one.

$sp must come back to exactly where it started. If a procedure returns with $sp four bytes low, nothing fails immediately. The caller's own lw offsets then read the wrong words, it restores garbage into $ra, and jr $ra jumps somewhere arbitrary. The symptom appears in the caller, long after the mistake. That is why this one is worth being rigid about.

7.12   When a procedure calls itself

Factorial, in any language you know:

fact(n) = 1 if n = 0 = n × fact(n-1) otherwise

And in MIPS, with the multiplication left as a comment for a reason we will come to:

fact: # base case: if n == 0, return 1 bne $a0, $zero, recurse li $v0, 1 jr $ra recurse: addi $sp, $sp, -8 # frame: $ra and our own n sw $ra, 4($sp) sw $a0, 0($sp) addi $a0, $a0, -1 # n - 1 jal fact # ← calls ITSELF. $ra and $a0 now belong to the new call lw $a0, 0($sp) # our n, back from our own frame lw $ra, 4($sp) addi $sp, $sp, 8 # $v0 = $a0 × $v0 ← the one thing this machine cannot do jr $ra
Recursion needs no new mechanism whatsoever

Look at what is in that procedure. jal, $ra, a prologue, an epilogue, jr $ra. Every one of them is from §7.11, doing exactly what it did there.

The only thing that is different is that the procedure being called happens to be this one. The hardware cannot tell — a jal to your own label is an ordinary jal. What makes recursion work is that each call gets its own frame, so each call's n and $ra are stored somewhere no other call will touch.

That is the answer to "how does it remember where it was" and it is not mysterious: the stack remembers, one frame per call, because $sp moved down before each one.

Why the multiply is a comment

Your ALU has seven operations and none of them multiplies. MIPS has mult, and MARS will run it — but the machine you are building could not, and this course has not taught it.

So fact is here as a teaching example, to show the frames. It is not on the assignment, and the optional bonus there uses a recursive sum, which needs only addition.

A stack overflow is not a mysterious failure

Call fact with a negative argument and the base case is never reached. Each call subtracts 8 from $sp, forever, and eventually $sp points below the region the operating system gave the stack. The next sw writes somewhere it is not allowed to and the program dies.

That is the whole of a stack overflow: $sp walking off the end of its region. Switch the visualiser above to recursion mode and watch $sp descend — there is nothing stopping it but the base case.

7.13   Both halves could finally choose

This week opened with a claim: the hardware and the software were missing the same thing. Take stock.

Hardware

A 3-bit opcode into a decoder, seven enable blocks, an OR combine. ALU_8BIT is finished, and it does not change again between here and Week 17.

Software

Branches, loops, jumps, calls, returns, a stack and a calling convention. Your programs can decide, repeat, and call — including calling themselves.

One idea, two places

Both halves of the week were the same thing: something that selects. A decoder raising one of eight lines, and a branch writing one of two values into the PC. Different circuits, same job — and it is why this course teaches the two tracks side by side instead of finishing one before starting the other.
