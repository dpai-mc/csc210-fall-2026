Fetch, Decode, Execute

Sections 9.5 – 9.8  |  Estimated time: ~1.5 hours

9.5   The loop

Page 1 ended on one rule: a word in memory is an instruction because the PC pointed at it. Everything a processor does follows from repeating three steps on whatever word that is.

  1. Fetch. Read the word at the address in the PC, and advance the PC to the next instruction.
  2. Decode. Work out what the word asks for: which operation, which registers, which constant.
  3. Execute. Do it — compute, read or write memory, or change the PC.

Then fetch again. There is no step 4 and no point at which the machine stops to think. A program is a list of words; running it is this loop, applied to each in turn, with branches and jumps doing nothing more mysterious than writing a different number into the PC during step 3. You worked out that number yourself in Week 7.

Three steps is the outline. To see what a real processor does inside each one, we need a real processor.

9.6   A real machine to watch

The machine on this page is the multi-cycle MIPS datapath, the textbook design from Patterson and Hennessy. It runs the same MIPS instructions you have been writing in MARS, and it was chosen for one reason: it is a stored-program machine in the sense of page 1. It has one memory, holding both the program and its data, and one ALU, and it takes several clock cycles per instruction so that each step of the loop gets a cycle of its own.

Dashed outlines: registers a MIPS program cannot name. Solid: things your code can see — the PC (through branches and jumps), the 32 registers, and memory.

Most of this you already own, at a smaller size:

  • PC — a register holding the address of the next instruction. Week 7 wrote numbers into it with branches and jumps.
  • Memory — one memory, byte-addressed, little-endian, the same one MARS shows you. Program at 0x00400000, data at 0x10010000. Week 8 built a small version of it.
  • Registers — $zero through $ra. Read two at once, write one. Week 10 builds a register file for your machine.
  • ALU — one ALU, used for every addition in the machine, including the ones the program never asked for. You built one in Weeks 6 and 7.

Five registers are new, and no MIPS instruction can name any of them. They exist because the work is spread across several cycles and something has to hold each cycle's result for the next one:

Where is the MAR?

Many textbooks list a memory address register among a CPU's parts, and you built one in Week 8. This MIPS design does not have one. The small selector marked addr chooses, each cycle, whether memory's address comes from the PC (to fetch an instruction) or from ALUOut (to load or store data), and the PC and ALUOut hold their values steady for as long as memory needs them. Same job, done by registers the machine needed anyway. Your machine does it with a real MAR; both are honest designs.

9.7   Five steps, one per clock cycle

On this machine the loop's three steps become up to five clock cycles. In each cycle a few registers take new values; the arrows below are register transfers, read “gets”. The first two cycles are identical for every instruction, because until the instruction has been decoded the machine does not know what it is.

CycleStepWhat happens
1FetchIR ← Memory[PC] and PC ← PC + 4. Memory reads the word the PC points at into the IR. At the same time the ALU adds 4 to the PC, so the PC already points at the next instruction.
2DecodeThe control unit reads the IR's opcode. A and B take the registers named by the rs and rt fields. The ALU, which has nothing else to do, computes PC + offset × 4 into ALUOut in case this is a branch.
3ExecuteDepends on the instruction: an R-type operation on A and B; base plus offset for a load or store; the comparison that finishes a branch; or the new PC for a jump.
4Memory or completionA load reads memory into the MDR; a store writes B to memory; an R-type or addi writes its result to a register and is finished.
5Write-backOnly a load gets here: the register file takes the MDR.

Two details in cycle 2 are worth stopping on. The branch target is computed for every instruction, including the ones that are not branches; the ALU is idle that cycle, so guessing costs nothing, and a branch that needs it finishes a cycle sooner. And A and B take rs and rt before the machine knows whether the instruction uses them. Reading a register you do not need is harmless; reading it a cycle late would cost a cycle.

    9.8   Counting cycles

    Run the stepper to the end. The program executes 19 instructions in 76 cycles before reaching syscall — an average of exactly 4.0 cycles per instruction. (The syscall itself is fetched and decoded, and then the machine hands control to the system, which this model does not include.) MARS, which does not model cycles, reports the same final values: $t1 = 25, sum = 25.

    Where the cycles go is worth reading off the table in §9.7. A load takes five because it uses memory twice — once to fetch itself, once to fetch its data — and on a machine with one memory those cannot happen in the same cycle. A branch takes three because it has nothing to write anywhere except, perhaps, the PC. Change the mix of instructions and the average changes with it; a loop full of loads is slower per instruction than a loop full of adds.

    “Average cycles per instruction” has a name, CPI, and in Week 15 it becomes one third of the equation for how long a program takes. The number you just got by stepping is the number that equation needs.
