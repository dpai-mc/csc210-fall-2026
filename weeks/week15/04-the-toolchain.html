Macros, Assemblers, Linkers, Loaders and Debuggers

Sections 15.13 – 15.16  |  Estimated time: ~45 minutes

Since Week 5 you have typed assembly into MARS and pressed Assemble, and since Week 14 you have put bytes into your own CPU’s RAM. A whole set of tools sits between the text you write and the bytes a processor runs. This page names them, using things you have already done.

15.13   Macros

A macro is a named piece of assembly text. Wherever you write its name, the assembler pastes in the text, with any arguments substituted, before it assembles anything. The processor never sees the macro, only what it expanded to. You have met two kinds already:

  • Pseudo-instructions (Week 7): blt $t0, $t1, L is not a MIPS instruction; MARS expands it to slt + bne. These are macros built into the assembler.
  • MOV and SUB on your CPU (Week 13): not instructions either, but sequences of NOT and ADD that you wrote out by hand. An assembler that expanded them for you would be treating them as macros (the assembler in 15.14 does).

MARS lets you write your own. Two that every MIPS programmer ends up wanting, push and pop, using only the stack instructions from Week 7:

.macro push (%r) addi $sp, $sp, -4 sw %r, 0($sp) .end_macro .macro pop (%r) lw %r, 0($sp) addi $sp, $sp, 4 .end_macro .data .text addi $t0, $zero, 7 addi $t1, $zero, 9 push ($t0) push ($t1) pop ($t0) # $t0 = 9 pop ($t1) # $t1 = 7: swapped addi $v0, $zero, 10 syscall

%r is the macro’s parameter; push ($t0) becomes the two lines with $t0 in place of %r. A macro has to be defined before it is used, so the definitions come first. After assembling, MARS’s Text Segment shows the expanded instructions, eight of them before the exit, with no trace of the names push and pop.

A macro saves the call and return and spends memory doing it, which is the right trade for something two or three instructions long. It also hides the instruction count from page 1: one line of source, several instructions executed. SUB R1, R2 looks like one instruction and costs three.

15.14   The assembler’s two passes

An assembler turns each line of source into bytes. That is easy until a line refers to a label that has not appeared yet. In Week 14’s sum loop, JZ jumps forward to the END. To encode it, the assembler needs END’s address, and when it reaches the JZ it has not seen the END yet. You solved this by hand in Week 14 by counting bytes first. An assembler does exactly that, in two passes:

  1. Pass 1 walks the source counting bytes, without encoding anything. Every time it meets a label it writes the label and the current address into the symbol table.
  2. Pass 2 walks it again and encodes every line. Any label it meets is now in the table, whether it was defined above or below.

MARS does the same for MIPS. Its Labels window (Settings → Show Labels Window) is its symbol table, and Week 7’s branch offsets are what pass 2 works out from it.

15.15   The linker and the loader

Real programs are not one file. Each source file is assembled on its own into an object file: machine code, plus a list of the labels it defines and the labels it uses but does not define. Two more tools finish the job:

  • The linker joins the object files into one program. It decides where in memory each file’s code and data go (moving them from where the assembler assumed, called relocation), and fills in every address that crossed from one file to another. In MIPS, .globl total marks total as a label other files may use; without it the label is private to its file.
  • The loader puts the linked program into memory, sets up the stack pointer and the PC, and starts it. You built one. In Week 14, RESET put the PC at 0, and LOAD walked COUNTER_256 through the external RAM, copying the program into your CPU’s RAM.

That is why course programs never need .globl main: each one is a single file, nothing needs to be linked to it, and MARS starts at the first instruction in .text. MARS can assemble several files together (Settings → Assemble all files in directory); this course never asks you to.

15.16   Debugging tools

A debugger lets you run a program a piece at a time and look inside the machine while it runs. You have been using them since Week 5 without the name.

  • MARS, on the Execute tab:
    • Step (F7) runs one instruction; Backstep (F8) undoes one.
    • Breakpoints: tick the Bkpt box beside an instruction in the Text Segment, then Run (F5). MARS runs at full speed and stops before that instruction, every time it reaches it.
    • The Registers pane highlights the register that just changed, and the Data Segment shows memory. These are your watches.
    • The run speed slider slows execution down so you can watch it. Tools → Instruction Counter counts the instructions a run executes: page 1’s IC, measured.
  • Logisim is a debugger for hardware: Tick Once runs one quarter, the poke tool sets a pin, a probe shows any wire’s value, and Week 13’s test port let you drive the bus by hand.

Tools are half of it. The other half is Week 13’s method: say what should happen before you step, then step and compare. A debugger only shows you what did happen; you have to supply what should have.

Try it: a breakpoint in a loop

.data .text addi $t0, $zero, 5 # n add $t1, $zero, $zero # sum loop: add $t1, $t1, $t0 addi $t0, $t0, -1 bne $t0, $zero, loop addi $v0, $zero, 10 syscall

Assemble it, tick Bkpt beside the bne, and press Run. Before you do, write down what $t0 and $t1 will hold at each stop. MARS stops before each bne: $t0 = 4, 3, 2, 1, 0 and $t1 = 5, 9, 12, 14, 15. Press Run again at each stop; after the fifth, the loop falls through and the program exits. This is optional and not graded.
