Pydantic AI up close

Pydantic AI is the library that turns "send text to a chatbot" into "get back a filled-in, checked form." Here is a simplified version of how the agent asks for one page review. It is shorter than the real code, but it uses the same ideas.

from pydantic import BaseModel, Field
from pydantic_ai import Agent, ModelRetry
from pydantic_ai.models.openai import OpenAIChatModel
from pydantic_ai.providers.openai import OpenAIProvider

# ① The form the model must fill in
class PageReview(BaseModel):
    topics: list[str] = Field(description="COR topic ids taught")
    level: int = Field(ge=1, le=3)        # 1, 2 or 3 only
    cslos_assessed: list[str]
    observations: list[str] = Field(max_length=8)

# ② Which model: here, the local server
local = OpenAIChatModel(
    "qwen3.8-27b-q8-dualgpu",
    provider=OpenAIProvider(
        base_url="http://127.0.0.1:8083/v1", api_key="none"),
)

# ③ The agent: instructions + form
agent = Agent(
    local,
    output_type=PageReview,
    instructions=open("specs/review_page.md", encoding="utf-8").read(),
)

# ④ A check written in plain code
@agent.output_validator
def check(review: PageReview) -> PageReview:
    if not review.topics:
        raise ModelRetry("No COR topic listed. Name at least one topic id.")
    return review

# ⑤ Run it
result = agent.run_sync(page_text_and_cor)
print(result.output.topics, result.output.level)
  1. The form. A Pydantic model (a Python class) says exactly which fields the answer must have and what values are allowed. A level of 4 or a missing list is rejected automatically.
  2. The model connection. The local server speaks the same "OpenAI-compatible" language as cloud services, so swapping in a frontier model means changing this one line. Nothing else changes.
  3. The agent. Instructions come from a plain text file (a "spec"), so they can be improved without touching the Python.
  4. The check. ModelRetry sends the answer back to the model with the reason, and the model tries again. This is the "bad answers are sent back" loop from the architecture page.
  5. The result is a real Python object, not a paragraph of text to pick apart. result.output.level is guaranteed to be 1, 2 or 3.

One gotcha from the project: the local model's chat format rejected one way Pydantic AI sends retry messages. The fix was a small custom layer, built with httpx, that rearranges the messages before they reach the server.

The .venv: a private toolbox for one project

A virtual environment is a folder, here named .venv, that holds its own copy of Python and its own installed libraries. Think of it as a toolbox that belongs to one project. Without it, every project on the computer shares one big drawer, and upgrading a library for one project can quietly break another.

The recipe card: pyproject.toml

How does pip install know which libraries to fetch? The project has one settings file that lists them. A simplified version:

# pyproject.toml (simplified)
[project]
name = "course-agent"
requires-python = ">=3.10"
dependencies = [
  "pydantic-ai-slim[openai,anthropic]",
  "openpyxl",
  "pyyaml",
  "pypdf",
  "playwright",
]

[project.optional-dependencies]
dev = ["pytest"]

[project.scripts]
course-agent = "course_agent.cli:main"
  1. dependencies: what every user needs. [openai,anthropic] means "only the connectors for these providers," which is why it's the slim package.
  2. dev: extras needed only by the developer, here the test tool. That's the [dev] in pip install -e ".[dev]".
  3. scripts: creates the course-agent command, so you don't have to type python -m … every time.
  4. A file called .gitignore keeps .venv/, secrets (.env) and the output workspace out of version control. The toolbox is rebuilt from this recipe, not copied around.

Lessons about tools

Use the library, not your own

Reading PDFs, driving a browser and writing Excel files are solved problems. Using tested libraries left the effort for the part that's actually new.

Standards make AI swappable

Because the local server speaks a common API, the same agent runs on a free local model or a paid frontier model. You aren't locked in.

Ask for structure, then check it

Pydantic turns "please answer in JSON" into a guarantee, and anything that fails the check goes back to the model with the reason.

Versions matter

The tests ran on one version of Pydantic AI (2.54) and the instructor's machine had another (2.69), and the two report "out of tokens" differently. The code now checks for both. Recording versions saves debugging time.

Small defaults bite

Windows reads text files as cp1252 unless told otherwise, which garbled every dash and arrow in the course pages. Every file read now says encoding="utf-8".

Isolate the project

The .venv means the agent's libraries can't break, or be broken by, anything else on the computer, and the whole setup can be rebuilt from one file.

Discussion questions

  1. Pydantic AI forces the model's answer into a fixed form. What do you gain? Could anything useful get lost because it doesn't fit the form?
  2. Changing one line switches the agent from a local model to a cloud model. Who should be allowed to change that line, and when?
  3. Every library is code written by strangers. How would you decide whether a library is trustworthy enough to handle course or student data?
  4. Why might an instructor keep the model's instructions in a text file (a "spec") instead of inside the Python code?
